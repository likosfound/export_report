 macOS supply chain attacks

В третьем посте серии #macOS расскажем, как злоумышленники атакуют цепочки поставок macOS. Такие атаки — один из самых эффективных способов осуществить первоначальный доступ, поскольку зачастую они обходят проверки безопасности системы из-за способов запуска/доставки полезной нагрузки на хост.

 Существует множество векторов подобных атак:

  • Xcode Run Script phase;
  • CocoaPods Podfile/Podspec;
  • Swift Package Manager;
  • Homebrew formula;
  • Python pip setup.py & pyproject.toml;
  • npm/yarn/pnpm lifecycle scripts;
  • Makefile (poisoning);
  • IDE configuration.

Все перечисленное позволяет добавлять произвольные shell-команды, выполняющиеся при стандартных для пользователя (часто разработчика) условиях: сборке проекта, установке пакета/зависимостей, установке расширения и т. п.

Ниже более подробно про некоторые сценарии атаки.

Xcode Run Script phase

Проекты Xcode описываются в бандле .xcodeproj, который, помимо прочего, содержит файл project.pbxproj — текстовый plist, описывающий исходные файлы, настройки сборки и фазы сборки проекта. С точки зрения атаки интересна фаза PBXShellScriptBuildPhase, используемая для выполнения shell-скриптов при сборке проекта. Эта функциональность используется для легитимных целей: настройки окружения, управления зависимостями, компиляции и т. п.

Однако атакующие, добавив несколько строк в популярный проект (или в проект во внутрикорпоративной системе управления версиями), могут использовать PBXShellScriptBuildPhase для закрепления, загрузки следующего стейджа, разведки окружения и пр.

Обнаружить выполнение подобных скриптов несложно: либо по родительскому процессу xcodebuild, либо по переменным окружения процесса SRCROOT, BUILT_PRODUCTS_DIR, DEVELOPER_DIR.

Однако действия, обычно являющиеся подозрительными, в контексте сборки проекта могут оказаться вполне легитимными: создание LaunchDaemon, компиляция, osascript и т. п. Например, проекты, которые используют osascript, можно найти на GitHub по запросу (path:*.pbxproj PBXShellScriptBuildPhase osascript). Помимо регулярного анализа выполняемых таким образом скриптов в рамках threat hunting, можно попытаться выявить действия, которые даже в контексте сборки проекта будут подозрительными:

  • network connection к хостам, не относящимся к Apple или пакетным менеджерам, от дочернего процесса xcodebuild;
  • обращение к keychains или TCC data от дочернего процесса xcodebuild.

Например:

dev_os_type: macos AND
event_type: (ProcessCreateMac OR ProcessInfoMac) AND
cmdline:(
    "*/Library/Keychains/*" OR
    "*login.keychain-db" OR
    "*login.keychain" OR
    "*System.keychain*"
) AND
(
    proc_env: (SRCROOT OR BUILT_PRODUCTS_DIR OR DEVELOPER_DIR)
    OR
    proc_p_file_path: xcodebuild
)

CocoaPods Podfile/Podspec

CocoaPods — это менеджер зависимостей для iOS- и macOS-проектов. В каждом проекте есть файл Podfile, в котором перечислены зависимости, а в каждой библиотеке — файл .podspec, описывающий порядок ее сборки. Оба файла написаны на языке Ruby и выполняются при вызове pod install и pod update.

Podfile поддерживает блоки pre_install и post_install, в которых запускается произвольный код до и после установки зависимостей. В легитимных проектах это используется для настройки параметров сборки, добавления пользовательских фаз сборки и исправления зависимостей. Блок post_install имеет доступ ко всей конфигурации рабочей области Xcode: к каждой цели, каждому параметру сборки и каждой ссылке на файл.

Podspecs поддерживают script_phases (скрипты оболочки, встроенные в фазы сборки Xcode пользователя) и prepare_command (команда оболочки, выполняемая при первой загрузке pod, до его установки). Библиотека, использующая prepare_command, выполняет эту команду на каждом компьютере, на котором запускается pod install с этой библиотекой в качестве зависимости.

Подменив содержимое Podfile или .podspec, злоумышленник обеспечивает выполнение своего кода на компьютерах разработчиков, на которых запускается команда pod install.

Swift Package Manager

Swift Package Manager (SwiftPM) — это система сборки и менеджер зависимостей для проектов на Swift. Каждый проект SwiftPM содержит Package.swift — манифест, в котором объявляются цели, зависимости и плагины.

Плагины бывают двух типов:

  • Плагины инструментов сборки. Запускаются при каждом выполнении команды swift build (а также при каждой сборке в Xcode, включающей данный пакет). Это исполняемые файлы на языке Swift, скомпилированные SwiftPM и запускаемые в песочнице с доступом только на чтение к исходному каталогу и доступом на чтение и запись к каталогу вывода.
  • Плагины команд. Запускаются, когда разработчик явно выполняет команду swift package plugin <verb> (относительно редкое событие).

Оба типа получают контекст пакета и могут вызывать команды оболочки через Process(). Внедряя вредоносный плагин в файл Package.swift, злоумышленник добивается выполнения кода во время вызова команд swift build или xcodebuild.

Homebrew formula

Homebrew — это наиболее распространенный пакетный менеджер в macOS. Каждый пакет определяется Ruby-файлом (формулой) Formula/<package>.rb внутри tap-репозитория. Формула определяет, как загружать, собирать и устанавливать ПО. Три блока в этом Ruby-файле позволяют выполнять shell-команды посредством system():

  1. 1.
    install. Выполняется во время brew install.
  2. 2.
    post_install. Выполняется после окончания установки.
  3. 3.
    test. Выполняется во время brew test.

Tap-репозиторий — это Git-репозиторий формул. Значение tap по умолчанию — homebrew-core (https://github.com/homebrew/homebrew-core), но можно добавить внешний репозиторий командой brew tap username/repo. Данная команда склонирует https://github.com/<username>/homebrew-<repo> в Hombrew-tap-директорию ($(brew --repository)/Library/Taps, часто /opt/homebrew/Library/Taps). Дальнейший вызов brew install username/repo/package установит в системе пакет.

Однако существует способ и локального добавления tap-репозитория с помощью второго аргумента brew tap (локальной директории):

brew tap hacker/hacktools /tmp/hacker/homebrew-hacktools/Formula/hack.rb
brew install hacker/hacktools/hack

Таким образом, атакующий может получить выполнение в контексте Ruby, либо загрузив полезную нагрузку с GitHub или из другого источника, либо создав файл локально. Помимо регулярного поиска подозрительных tap-репозиториев, подобную атаку можно детектировать правилом, обнаруживающим добавление tap-rep из локальных файлов в подозрительных директориях:

dev_os_type: macos AND
(
    cmdline.keyword:/.*brew tap[^|&>]+?\/(tmp|var|dev)\/.*/
)

Заключение

Детектировать атаки supply chain трудно, поскольку действия, выполняющиеся на разных этапах сборки/установки проекта, часто попадают под типичные критерии «подозрительных» (curl внешнего endpoint для загрузки зависимости, установка LaunchDaemon, копирование/запуск скриптов из /tmp и т. п.).

Однако проблема решаема: необходимо понять, что происходит в инфраструктуре во время сборки/установки проектов, и исключить найденную легитимную активность из правил обнаружения. Например, сам по себе curl к внешнему endpoint во время той или иной стадии сборки встречается часто, однако в организации будет аномалией, если из 100 хостов, на которых происходила установка, curl выполнился только на одном.

Также в детектировании может помочь более строгая спецификация подозрительных действий: обращение к keychains, изменение TCC, явное создание пользователя или нетипичная для проекта разведка окружения (например, доменного). Но даже с применением всех рекомендаций по обнаружению советуем отсматривать выполняемые во время сборки команды (или определенные паттерны) в рамках threat hunting, чтобы значительно увеличить область видимости команды безопасности.
